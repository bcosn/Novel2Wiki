# 开发记录与想法

## 2026-10-14

- 已确认 v0.3 范围，条目生成策略保持现状；关联跳转留至 v0.3fix。
- 当前 merge_append 已先验证全部内容，但多个 JSON 的逐文件替换不构成跨文件事务；SQLite 应成为权威数据源，导出文件可重建。
- 当前合并脚本重编号会影响增量和用户附件；存储采用稳定记录 ID，不因显示顺序重编号。
- SQLite 的单写事务不要求主 agent 搬运结果；各工作进程调用提交程序即可。
- 子代理生成本身仍有 tokens 开销；路径协议只能避免后续重复传递，不能把初次生成算作零成本。
- 保留现有格式后端，lxml 仅替换解析实现；原文件保留、清洗版本可追踪。
- 原 EPUB 解析依赖双引号与固定命名空间前缀，应该使用 XML 结构解析，并保留 spine 顺序。
- EPUB/HTML 的文本提取需要专门处理段落、br、ruby 注音与脚注，不直接使用无分隔的 text_content。
- 新依赖：lxml、charset-normalizer；SQLite 通过 Python 标准库。EbookLib 的 AGPL 许可不引入本版。
- 清洗及任务缓存按输入内容、规则/配置版本计算；不使用文件名作为缓存身份。
- DSH 的已安装包不等于实际挂载插件，挂载插件也不等于模型收到的工具；分别记录证据。
- GitHub 网络直连缓慢，开发基线采用本地冻结 v0.2fix 包及现有 skill，测试与许可证来自分发包。
- GitHub 克隆随后完成，正式开发已迁移到 main 的独立 checkout，分支 v0.3-core；原目录与试验未覆盖。
- 并行抽取不能直接替换整张表；结果按记录身份合并，同身份不同值拒绝。条目全稿替换使用乐观版本检查。
- 默认 headless 仍挂载 web、subagent、MCP resources 等组件，需专用 overlay 明确禁用；不删除用户全局插件。
- 重复图片共享内容文件；删除关联不立即删除文件，避免破坏其他上传和备份，后续再设计垃圾回收。
- review_plan 的 JSON 锁文件在进程被终止后可能残留；保留审查策略，将 CLI 台账提交迁移到 SQLite。JSON 丢失不能重置额度。
- 合并批次保留原 ID，编号缺口合法；悬空链接在写文件前拒绝，不再静默删除或重新编号。
- DSH 请求审计中的消息 UUID 是本地持久化字段，不是提示词；缓存稳定性比较 role/content，另用真实用量验证。
- 已完成 49 项程序测试和极小 DSH 实测：第二次固定请求读取 3456 缓存 tokens、169 未缓存输入；不外推长篇收益。
- 后续想法：完整快照的压缩与保留策略、附件垃圾回收、导出目录的版本切换、客户端上传入口。均不扩大本版范围。
- v0.3fix 可复用现有事件参与者与条目 ID 自动构造关联；不安排额外全库关系分析代理。

## 《药》全文对照结果与后续发现

- 旧版和新版首次运行均到达相同的 16384 单次输出上限。会话记录显示，两次截断的消息都只有 reasoning，没有完成工具调用；旧版停在条目筹划，新版停在抽取筹划。因此不能把原因简单归为大文件写入，更不能把新版尚未完成的低成本当作节省。
- high 推理会在正式落盘前规划全篇全部表。后续要把任务拆成确定的阶段和小批次，每批完成立即提交，续跑读取阶段状态；仅在提示词中写“小批量”不足以证明能稳定完成。
- 对照统计必须包含截断、续跑、子代理和自动标题调用，按请求计量，再与会话记录核对。活动耗时按各次运行相加，不能把等待另一组的间隔算进去。
- 同一篇《药》抓取后遗留了网页末尾 Public domainPublic domainfalsefalse。本次为保留公平性不改变已冻结输入；这属于抓取遗漏，后续清洗应增加网页页脚识别与报告，不应事后称为有意设计的噪声测试。
- 旧版独立审查子代理也耗尽单次输出额度；作品级已领取的审查次数仍应计入，不能为拿到成功结果重建台账或重复领取。对照必须单列审查成功/失败，不能用脚本检查通过冒充语义审查通过。
- 两组本次审查均采用文件路径传参，未在创建消息里复制全文；旧版已经这样做。因此本例不能把节省全部归因于“新版路径协议”。新版审查消息指定独立输出文件、短返回，实际没有携带输入 hash / manifest；后续需要在执行入口强制校验协议，而不只依赖文档。
- 新版读取规范、分批提交与修正引文的调用明显增加；工具精简的收益必须与这些调用的累计代价一起看。下一步优先批量读取当前阶段所需规范、从已存证据直接引用，减少手工重打引文和逐项修复。

- 两组站点均完成，各续跑一次。旧版估算费用 ¥0.863329、新版 ¥0.887978，增加 2.86%；总 tokens 7,677,393 → 13,396,666（+74.49%），模型调用 54 → 114。输出 tokens 与未缓存输入下降，但反复调用增加的缓存输入抵消了费用收益。本次没有达到总体省耗目标。
- 缓存命中比例 98.37% → 99.24%，提升约 0.87 个百分点；仍须结合总输入判断。旧版 22 条/7189 正文字符，新版 24 条/7135 正文字符；八表抽取行数不同，不是严格同产物/同质量控制实验。
- 两组引文、人称、表结构、站点、条目链接最终均无脚本错误；独立审查均触发输出上限，没有第三方结论。人工抽查发现说话人错置、坟墓指代与「两半个馒头」改写失真，不能声称质量相同。
- 新版数据库 WAL 完整性检查 ok，章节、八表、正式条目及审查台账均与导出 JSON 一致。本次 jobs 为 0，审查没有完整落实任务 manifest/claim 链；这是执行入口下一步要约束的点。
- 另修审查失败台账：新增 --record-failure，明确保留 model_failed 与短原因，已领取次数不退还，不把无结论记成通过，不自动重试。此修补在冻结对照后完成，不改本次组内代码和用量，不宣称重跑过文章节省测试。

## 2026-10-15：条目结构、主次与公共设定页

- 发现旧importance只在人物表中暂标，写作入口没有消费它；种族表即使存在也经常没有页面。新增显式entry_plan：完整候选存文件，保留独立/短页/并入/留表/待判断五种去向，未知不等于次要。现有页保留，内容并入不等于别名或实体重定向。
- 按用户澄清，先根据原文判断种族、等级体系或普通属性，不写死字段名、品阶值、排序和成员。新增通用concept设定页，优先体系总览；是否拆各值由证据判断，不见表就自动造页。
- 规划每次最多6个候选或明确小范围表，写作1–3页；上下文12000字符，摘要6000字符。显式主题收窄姓名候选引用，写作只带所需证据；长章可显式选段并报告部分范围，不截断冒充读完。
- 主题边界、引用范围、空正文、合并主体及alias误用由程序检查。关系每方向分别声明原文，程序复制引用；目标发布后显示链接，追加设定页不重写旧人物正文。重建默认保留正式关系，显式空图才清空；旧来源hash不明或过期要求复核，防止重绑段落。
- 最终审查修复：空节也能通过、全书姓名命中强塞小包、resume丢计划覆盖状态，以及仅改另一页时清空旧关系。新增63项回归，当前159项通过；虚构4页分类例含历史状态、双向链接和待判断项。
- 两轮各727字符《药》节选、两人物页，保持quality-v2/Flash/high/8192/11工具，无生成子代理或独立审查。新版费用分别+37.29%/+53.61%，4组已知生成费用估算¥0.34223720；失败、无效字段返修与多读文件不剔除。事后匿名标签核对加主代理来源检查，不是人类盲评。
- 第一轮短页只剩习惯而漏出场行动；第二轮恢复行动，但仍有标题“服药”定性、补足安放凳子和让坐主体、必要事实只部分覆盖。结构通过不等于语义正确，未宣布质量或省耗通过。两轮结果均保留，后续模板/通用指引仅程序回归，不追加第三轮模型。
- 新想法：受控入口让模型决策和正文各写一次，减少自行翻规范、加无效字段与重复自改；为核心事实分配去向而非按篇幅压缩；在不同题材验证公共设定判断。暂不增加全库关系分析代理，不引入固定作品词表，不启用百科语料或小模型。
